## 1. Overview / Цель

Сделать настольное приложение, в котором человек подключает Google, выбирает папку и вручную синхронизирует контакты в обе стороны. Файлы принадлежат пользователю, читаются обычным редактором и агентами. Первый результат не должен требовать знания API, а последующие синхронизации должны объяснять изменения и помогать исправлять ошибки.

Outcome contract:
- Исходное поручение: все поля Google-контактов, Google → файлы и файлы → Google, для начала ручной запуск, простое подключение и UI/UX с перспективой распространения.
- Success means: исходный сценарий доказан на тестовых контактах реального Google-аккаунта, данные не исчезают при обычном цикле чтения/записи, конфликты не перезаписываются молча, пользователь видит подтверждённый результат каждого действия.
- Output EXEC: исходники, запускаемая Windows-сборка, спецификация формата, локальные инструкции подключения/сборки, автоматические тесты и визуальное evidence. Готовность локальной сборки, реальной интеграции и публичного выпуска отмечаются отдельно.
- Stop rules: SPEC заканчивается только после проверенного дизайна и review. EXEC не объявляется полностью завершённым без обязательных проверок; недоступность аккаунта или OAuth — конкретное ограничение интеграционной проверки, а не доказательство её успеха. Публикация, регистрация внешнего OAuth-проекта и изменения настоящих контактов требуют соответствующего поручения.

## 3. Проблема

Пользователю нужен редактируемый локальный экземпляр адресной книги, который возвращает правки в Google без потери богатых полей, ручной рутины и непонятного разрешения конфликтов.

## 4. Цели дизайна

- Полнота данных в пределах публичного Google API с явной картой возможностей, включая фото, ярлыки, избранное и нестандартные поля.
- Контроль изменений: план до записи, трёхстороннее сравнение, журнал операций и восстановление.
- Короткий обычный путь: подключение → папка → просмотр → применение; ошибки объясняются на языке действия пользователя.
- Независимое от UI ядро; подменяемые часы, файловая система и Google gateway для тестов с отказами.
- Версионируемый открытый файловый контракт; повторное открытие папки и перенос на другой компьютер без токенов в файлах контактов.

## 5. Non-Goals (чего НЕ делаем)

- Фоновый демон, автосинхронизация, mobile/web клиент, синхронизация нескольких аккаунтов между собой, CardDAV и другие провайдеры.
- Полноценный визуальный редактор адресной книги: в v1 UI показывает/сравнивает все поля и разрешает конфликты, обычное редактирование возможно в файлах.
- Автоматическое объединение людей по совпадению имени/телефона, очистка адресной книги или автозаполнение данных.
- «Другие контакты» Google, корпоративный каталог, история и корзина Google не входят в коллекцию обычных контактов. Это прямо указано в onboarding и справке. Их включение потребует отдельного контракта и scopes.
- Обход ограничений API ради полей веб-интерфейса, которых API не отдаёт. Нельзя обещать буквальное покрытие всех внутренних данных Google.
- Выпуск macOS/Linux, автоматический updater, выбор публичной лицензии, покупка сертификата, размещение сайта, публикация и отправка на проверку Google в текущем EXEC. Архитектура сохраняет возможность следующих платформ.

### 6.2 Детальный дизайн

#### 6.2.1 Полнота полей

«Все поля» означает: все документированные доступные поля контакта выгружаются; все документированные writable поля можно изменить файлом и отправить; read-only/недоступное явно отличается от редактируемого. Нельзя тихо пропускать поле и показывать «всё синхронизировано».

| Категория | Контракт v1 |
| --- | --- |
| Поля `updateContact` | `addresses`, `biographies`, `birthdays`, `calendarUrls`, `clientData`, `emailAddresses`, `events`, `externalIds`, `genders`, `imClients`, `interests`, `locales`, `locations`, `miscKeywords`, `names`, `nicknames`, `occupations`, `organizations`, `phoneNumbers`, `relations`, `sipAddresses`, `urls`, `userDefined`: полный вложенный JSON, массивы, custom types и поддерживаемые subfields. `memberships` обрабатывается через ярлыки/избранное ниже. [G1] |
| Фото | Скачивание доступного контактного фото, замена/удаление локального фото через специальные photo endpoints. Default avatar не считается загруженным фото. Изображения PROFILE доступны только как read-only. Google может перекодировать фото: исходный загруженный файл остаётся в backup, byte-identical roundtrip сервера не обещается. [G4] |
| Ярлыки и избранное | Каталог пользовательских групп, создание/переименование/удаление группы, членство и starred. Удаление группы никогда не удаляет входящие контакты. Системные ограничения Google сохраняются. [G5] |
| Read-only | Метаданные, вычисленные/форматированные значения и данные источника PROFILE сохраняются в `google.person`, показываются с подписью «Только чтение». Их изменение в файле — диагностируемая ошибка; файл не исправляется поверх правки без выбора пользователя. [G2] |
| Поля вне masks | `fileAses` есть в Person schema, но отсутствует в документированных read/write masks; `skills` есть в read mask, отсутствует в write mask. Они не объявляются двусторонне поддерживаемыми. Полученные значения сохраняются, UI показывает ограничение. Deprecated поля, для которых Google прямо не возвращает данные, восстановить нельзя. [G1, G2, G3, G9] |
| Новые неизвестные поля | Сырой JSON сохраняется рекурсивно; никакой автоматической отправки неизвестного поля. Изменение такого значения блокирует соответствующую запись с объяснением. Если неизвестное поле присутствует внутри заменяемой категории и registry не доказывает, что оно output-only, блокируется любая запись этой категории, даже при изменении только известного соседнего поля: иначе полная замена может стереть unknown на сервере. Другие категории доступны. Capability registry версионируется и проверяется contract tests. |

Запрашиваются все разрешённые read-mask категории. CONTACT и PROFILE разделяются по source metadata: writable projection строится только из CONTACT. Нельзя скопировать телефон профиля в контакт лишь потому, что он присутствовал в объединённом Person. Для нескольких CONTACT sources без однозначного адресуемого источника — остановка этой записи и диагностический конфликт.

Полнота длинных массивов: list может ограничить телефоны/email до 100. При достижении 100 записей в любой из этих категорий выполняется `people.getBatchGet` с полной маской, проверяется status каждого результата. Частичный ответ не является полной базой для обновления массива. [G2, G10]

Registry также различает writable subfields и output-only subfields: например, сохраняется `sourcePrimary`, а вычисленный `primary` не отправляется. Singleton restrictions, custom labels, Unicode, ведущие `+`/нули телефонов, даты без года и нулевые компоненты частичных дат не теряются. Порядок массива не используется как идентификатор элемента. Форматирование Google не превращается в бесконечный цикл правок.

#### 6.2.2 Файлы и владение данными

```text
Выбранная папка/
  contacts/<uuid>.contact.json
  photos/<uuid>.<jpg|png>
  groups/<uuid>.group.json
  .contactmirror/workspace.json
  .contactmirror/state.db
  .contactmirror/backups/<run-id>/...
  .contactmirror/trash/...
```

Имена файлов на основе локального UUID стабильны при смене имени человека; понятное имя видно в JSON и UI. На экране есть «Открыть файл» и «Показать в папке». Переименование/перемещение файла внутри `contacts/` не создаёт новый контакт: identity берётся из `id`. Два файла с одним `id` — ошибка, а не две записи.

Сокращённый пример (настоящие документы могут содержать все writable категории):

```json
{
  "schemaVersion": 1,
  "id": "f4c23977-1b4a-40f2-b882-75f1a2bfb1c1",
  "data": {
    "names": [{ "givenName": "Анна", "familyName": "Примерова" }],
    "phoneNumbers": [{ "value": "+7 000 000-00-00", "type": "mobile" }],
    "birthdays": [{ "date": { "year": 0, "month": 5, "day": 12 } }],
    "userDefined": [{ "key": "Где познакомились", "value": "Конференция" }]
  },
  "labels": [],
  "starred": false,
  "photo": null,
  "extensions": {},
  "google": {
    "resourceName": "people/example",
    "person": {}
  }
}
```

- `data` — editable CONTACT projection; `labels` — UUID пользовательских групп; `starred` — системная starred membership. `data.memberships` не допускается, чтобы не было двух источников одной правки; полное исходное membership хранится в `google.person`. Неизменяемые системные memberships сохраняются отдельно и не удаляются при обновлении пользовательских ярлыков.
- `photo` — относительный путь внутри `photos/` или `null` для явного удаления. Отсутствующий файл по заданному пути означает ошибку, а не команду удалить фото. Read-only snapshot сохраняет оригинальные Google photo descriptors; доступные недефолтные read-only изображения кэшируются отдельно под `.contactmirror/`.
- Фото сравнивается по содержимому, а не только по пути: baseline хранит пару `acceptedLocalContentHash`/`acceptedRemoteContentHash` и подтверждённую связь между отправленным оригиналом и результатом перекодирования Google. Правка bytes по прежнему пути считается изменением. При upload после подтверждённого ответа и скачивания результата сохраняются оба hash, исходный локальный файл остаётся; следующее сравнение этой пары — no-op, даже если сервер перекодировал JPEG. При pull скачанные байты становятся локальным файлом и новой подтверждённой парой. URL/etag дескриптора сами по себе не заменяют проверку содержимого; remote image revalidation использует conditional GET, когда поддерживается, иначе скачивание. При конкурентной правке фото или crash до сохранения подтверждённой пары — recovery, без записи поверх новых bytes и без слепого повторного upload. Все photo hashes перепроверяются вместе с JSON hashes перед Apply.
- `google` — полная последняя полученная Person snapshot, включая неизвестные свойства и source metadata; только чтение. Operational source/etag берётся из state, не доверяется произвольно отредактированному файлу. `extensions` — локальные пользовательские данные, сохраняемые приложением, без отправки Google.
- Для существующей записи отсутствие writable категории, бывшей в baseline, либо `[]` означает очистку категории и явно показывается в плане. `null` внутри `data` и неверные типы не нормализуются молча. У новой записи отсутствие поля означает «не задано».
- Новый `.contact.json` создаётся командой UI «Новый файл контакта» с UUID и шаблоном либо вручную по JSON Schema. Отсутствующий UUID можно присвоить только явной командой исправления с preview. Для новой записи `google` отсутствует; наличие чужого resourceName не импортирует связь автоматически.
- Документ группы: schemaVersion/id/name/clientData/extensions/google snapshot. Неизвестный UUID ярлыка — ошибка. Новая группа создаётся перед зависимым добавлением membership. Зависимые операции не выполняются, если группа не создана.
- UTF-8, LF, стабильное форматирование. При чтении запрещены duplicate JSON keys, опасная неоднозначность числа/строки, чрезмерная глубина и oversized файл; лимиты документируются и дают явную ошибку, не обрезание. Для фото — проверка формата, размеров и декодирования. Пути не выходят из workspace, symlink/reparse points внутри дерева не обходятся.
- Токены хранятся вне выбранной папки: Windows DPAPI CurrentUser + ограниченный ACL в LocalAppData. Токены и OAuth codes никогда не входят в backup/логи/диагностику. Логи и диагностический export по умолчанию не содержат request bodies и имён/телефонов/email контактов. Backup, напротив, обязан содержать исходные персональные данные для восстановления. Контакты и backups — обычные незашифрованные пользовательские файлы; это коротко объясняется при выборе папки.
- `workspace.json` связывает folder ID, schemaVersion и Google issuer/sub. Email нужен только для подписи аккаунта. Смена аккаунта не переиспользует чужие baseline/операции; нужен другой workspace либо отдельная явная миграция вне v1.
- Папка с восстановленным state и совпадающим аккаунтом продолжает работу после re-login. Потеря/повреждение state включает Recovery read-only: reconstruct identity по source identifiers и snapshot, но не трактовать отсутствующие файлы как удаления. Новая baseline фиксируется только после полного сравнения и выбора, с backup старого состояния.

#### 6.2.3 Синхронизация

1. «Проверить изменения» берёт блокировку workspace, проверяет аккаунт, целостность manifest/state, читает локальные документы и полный paginated snapshot Google плюс группы. v1 намеренно использует full scan при каждом ручном запуске. Incremental sync/token — будущая оптимизация, не необходимая функция v1.
2. До завершения чтения всех страниц и нужных дополнений не выводятся удаления по отсутствию. Ошибка сети или частичный ответ оставляют прошлую baseline нетронутой. Файлы и Google не изменяются самим preview; новый snapshot и план остаются в рабочем состоянии приложения.
3. Planner сравнивает B (последнее согласованное значение), L (локальное) и R (Google). Unit of merge — целая writable верхнеуровневая категория, отдельные labels/starred/photo; массив внутри категории атомарен. Изменения имени и телефона с разных сторон объединяются; два разных изменения phoneNumbers требуют выбора.
4. План содержит входные hashes/source etags, account/workspace identity, операции, зависимости, before/after и причины conflict/block. Пользователь может применить бесконфликтные строки; пропущенные/конфликтные значения не становятся новой baseline.
5. Перед Apply повторно проверяются локальные hashes и актуальное удалённое состояние затрагиваемых контактов/групп, формируется durable journal и backup. При drift соответствующий план аннулируется, нужен новый preview. Проверка и резервирование повторяются перед конкретной записью; если backup не записан, запись не начинается.
6. Google mutations последовательны на аккаунт. PATCH отправляет только реально изменённые категории с полными значениями этих категорий и свежим CONTACT source etag. `failedPrecondition` переводит запись в conflict. Ответ write, а затем targeted read подтверждают серверное значение; list после write не используется как единственное подтверждение. [G1, G3]
7. Локальная запись использует временный файл в той же папке, flush и atomic replace, сохраняет исходную версию. Перед replace проверяется hash, на Windows используется file locking/share mode для защиты от параллельного редактора. При несовместимом открытом handle — «Файл занят», не overwrite. Старый handle/rename, конфликт синхронизатора папки либо расхождение после записи приводит к recovery; архив исходных байтов обязателен.
8. По каждой операции journal хранит planned/started/confirmed/failed/unknown и before/after. Baseline продвигается только по подтверждённым компонентам; запись полей, фото и memberships — отдельные checkpoints. Частичный результат не выдаётся за полную синхронизацию.
9. Отмена завершает текущую подтверждаемую операцию, останавливает следующие. После crash сначала recovery незавершённого run. Повторный Apply не пересоздаёт уже подтверждённые контакты.

Read-only mirror имеет отдельную ветку planner: изменение PROFILE/неизменяемых/неизвестных данных или фото при неизменном writable projection создаёт локальную операцию «Обновить сведения из Google». Она обновляет только snapshot/cache после проверки hash и backup, сохраняет текущие `data`, `labels`, `starred`, `photo` и `extensions`, не отправляет Google mutations и не меняет baseline неразрешённых editable-категорий. Изменение только служебного etag не считается пользовательским изменением; новый operational etag сохраняется с ближайшим подтверждённым checkpoint. В read-only snapshot никогда не записывается частично прочитанный Person вместо полного предыдущего.

Правка файла во время remote write: в journal заранее записан полный отправленный payload и исходный local hash. Если Google подтвердил A, а пользователь уже сохранил B, результат remote операции A фиксируется отдельно; текущий файл B не заменяется, показан статус «Google обновлён; в файле появились новые изменения». Общая baseline этого компонента остаётся прежней до reconciliation, operation-confirmed A исключает повторный create/write. Следующий preview сравнивает актуальные L/R с прежней baseline и предлагает конфликт либо подтверждённое согласование. Не применять старый план повторно и не продвигать baseline до нового пользовательского решения при таком drift.

Group membership собирается из полных Person данных; ограниченный `memberResourceNames` каталога групп не является доказательством отсутствия участника. Для group read запрашиваются `clientData`, `groupType`, `memberCount`, `metadata`, `name`. Удаление известной baseline-группы порождает связанный план снятия её UUID из `labels` затронутых локальных контактов после подтверждённого remote удаления; это не generic ошибка «неизвестный UUID». Новые labels, ссылающиеся на никогда не существовавшую группу, остаются ошибкой. Перед удалением группы список затронутых участников перечитывается: конкурентное добавление участника или изменение зависимого contact file инвалидирует план. Group delete всегда отправляет `deleteContacts=false`; удаления CONTACT этим endpoint не выполняются. Зависимый cleanup меняет только соответствующий label и snapshot, с per-file hash проверкой; при drift остаётся recovery checkpoint, не повторное удаление группы. Создание/переименование на уже занятое имя показывает конфликт 409 без автоматического слияния групп. Membership batches не превышают документированный лимит, `notFoundResourceNames` и `canNotRemoveLastContactGroupResourceNames` проверяются по каждому участнику даже при HTTP 200; confirmed записывается только после desired membership readback. Частичный отказ остаётся частичным результатом, а не общим успехом.

Google не даёт общей транзакции между полями, фото, группами и файлами. У delete/photo/membership endpoints нет подтверждённого CAS-контракта, равного `updateContact` etag: preflight read уменьшает, но не устраняет гонку с другим клиентом. UI и документация не обещают абсолютную атомарность. Для таких операций сохраняются свежие before-image и result, post-read проверка выявляет известный drift; обнаруженный конфликт не исправляется повторной разрушительной записью автоматически.

Неизвестный результат `createContact`/создания группы после timeout не повторяется слепо: состояние «Неизвестно, применилось ли изменение», повторное чтение и сопоставление кандидатов с выбором пользователя. Совпадение телефона или имени не доказывает identity. «Создать ещё раз» требует нового явно показанного плана с предупреждением о возможном дубликате. Аналогично ambiguous delete/update сначала проверяются чтением; auth/validation failures не retryable. Для retryable read errors — ограниченный exponential backoff с jitter, Retry-After и отменой.

Удаление локального файла создаёт предложение удалить контакт в Google; оно изначально не выбрано. Удаление в Google создаёт предложение переместить файл в локальную корзину; оно также не выбрано. Edit/delete — конфликт. Любое удаление требует выбора с видимой стороной; ≥10 удалений либо ≥20% baseline дополнительно требуют подтверждения числа. Пустая/недоступная/иная папка, утерянный manifest, незавершённое чтение, invalid JSON и повреждённый state никогда не превращаются в массовое удаление.

#### 6.2.5 Подключение и распространение

- OAuth Authorization Code + PKCE S256 + одноразовый state, внешний системный браузер, loopback listener на случайном порту только 127.0.0.1. Callback проверяет state; timeout/отмена закрывают listener. Используется поддерживаемая библиотека, не собственная криптография. [G6]
- Scopes: contacts для двусторонней работы, openid/email для устойчивого issuer/sub и подписи аккаунта. ID token проверяется библиотекой по issuer/audience/signature/expiry/nonce; email не служит ключом папки. Refresh token не попадает в workspace. [G11]
- Обычная release-сборка содержит идентификатор Desktop OAuth client издателя. Desktop client не является confidential client: его конфигурация не рассматривается как защищённый серверный секрет. Нет backend-посредника для передачи контактов.
- Для разработки есть отдельный advanced путь подключения OAuth-конфигурации издателя/разработчика. Отсутствующий client ID показывается как «Эта сборка пока не настроена для входа», не как ошибка пользователя. Demo/fake provider явно помечен и не считается Google sync.
- Для удобного публичного выпуска издатель готовит OAuth consent, People API, бренд/страницу приложения/privacy policy и проходит необходимую Google verification. Статус Testing подходит только для пилота: ограничения аудитории и срок авторизации отображаются в инструкции. Регистрация/публикация требуют отдельного поручения. [G7, G8]
- «Отключить аккаунт» удаляет локальные credentials; revoke Google grant — отдельное явно подписанное действие. Контакты в папке сохраняются. Повторный вход проверяет тот же sub. Все сетевые обращения приложения идут только к Google API/OAuth/официальным photo hosts; внешние URL из полей контакта не запрашиваются автоматически.
- Локальный v0.1: portable self-contained Windows x64 bundle. Публичная готовность отдельно требует реального first-run на чистой Windows, настроенного OAuth и решения о подписи/лицензии/канале распространения. Подготовленная сборка не называется опубликованным продуктом.

## 7. Бизнес-правила / Алгоритмы

| B/L/R для одной категории | Действие |
| --- | --- |
| L=B, R=B | Нет записи |
| L≠B, R=B | Предложить запись L в Google |
| L=B, R≠B | Предложить запись R в файл |
| L=R, оба ≠B | Признать согласованным после Apply, без лишней remote записи |
| L≠B, R≠B, L≠R | Конфликт |
| Удалено с одной стороны, с другой без изменений | Предложить удаление, не выбирать автоматически |
| Удалено с одной стороны, с другой изменено | Edit/delete conflict |
| Новый UUID без Google mapping | Create proposal, проверка похожих без auto-merge |
| Нет B при существующей Google mapping | Recovery/relink, не создавать дубликат и не удалять |

Canonical equality учитывает семантические writable значения и primary selection, исключает server etags/formatted output. Массивы сравниваются как мультимножества канонических объектов с учётом повторов, не удаляют одинаковые элементы. Не переписывать исходную пользовательскую строку телефона только ради сравнения. Неизвестные nested поля сохраняются и блокируют replacement соответствующей категории, если их output-only природа не известна registry. Любое изменение read-only части пользователем блокирует запись и остаётся видимым; обновление этой части из Google идёт отдельной mirror-операцией.

Identity переживает смену `resourceName`: matching по ACCOUNT+CONTACT source.id, сохранённым alias/previousResourceNames; при collision/many-to-one в результате Google merge — конфликт relink, без auto-delete/create. По имени/телефону identity не устанавливается. Удаления считаются только относительно полной и достоверной baseline того же workspace/account.

## 8. Точки интеграции и триггеры

- UI `CheckChangesCommand` → `PrepareSync(workspace, cancellation)` → `SyncPlan`.
- UI `ApplySelectedCommand(planId, selection, resolutions)` → revalidate → durable execution → `SyncRunResult`.
- `IGoogleContactsGateway`: paginated read, targeted full read, field update/create/delete, photos, group catalog/memberships; raw JSON boundary, typed operation result.
- `IWorkspaceStore`: validate/read, compare-and-replace, snapshot, journal/baseline checkpoints, restore-to-staging. `ICredentialVault`: save/load/delete; `IClock` и `IRetryPolicy` подменяются в тестах.
- Старт приложения обнаруживает незавершённый run до разрешения новых Apply. Файловый watcher в v1 лишь помечает preview устаревшим; никогда не выполняет sync сам. Даже без watcher hashes перепроверяются.
- Внутренние C# API не обещаются стабильными сторонним потребителям. Публичный стабильный контракт v1 — файлы/JSON Schema и описанные операции пользователя.

## 9. Изменения модели данных / состояния

- Persisted: workspace/account/source mapping, schema versions, baseline по компонентам, hashes, runs/operations, backup manifests, unresolved outcomes, OAuth metadata без токенов в workspace.
- Calculated: diff, список конфликтов, выбор операций, отображаемые counts. План устаревает при входном drift и после закрытия/перезапуска; применять сохранённый stale plan нельзя.
- На SQLite используются транзакции checkpoint и уникальные ограничения identity. DB и backup нужны для восстановления; их наличие не означает, что Google был откатан.
- Backup включает байты затрагиваемых файлов, фото, remote before-images, metadata/manifest/hash; создание нового контакта тоже отражается в journal с подтверждённым Google ID.

## 10. Миграция / Rollout / Rollback

- Первый запуск создаёт только структуру после явного выбора папки; первая синхронизация всегда показывает план.
- Формат v1 не имеет унаследованной миграции. Будущая версия: backup, migration транзакция, rollback при failure; более новый schemaVersion не открывается на запись старой версией.
- Восстановление выбирает run/контакт и создаёт staging diff относительно ТЕКУЩЕГО Google/локального состояния. Restore → новый preview и Apply, а не массовая перезапись live state из backup.
- Google delete нельзя честно обещать обратить с тем же resourceName: возможное восстановление создаст новый контакт и может не вернуть внешние связи/неизменяемые поля. Это видно до удаления. Локальная корзина и backup дают доступ к данным, но не глобальную транзакцию.
- Backup автоматически не удаляется в v1; UI показывает объём и предлагает ручную очистку выбранных старых runs. Очистка активного/unresolved run запрещена.
- Публичный rollout отдельно: publisher OAuth, privacy/consent/verification, лицензия/подпись, clean-machine smoke, только затем пользовательское разрешение на публикацию. Ни локальная сборка, ни approval SPEC не выполняют эту публикацию.

## 12. Риски и edge cases

- Google API не равен веб-продукту; fileAses/skills/PROFILE и новые поля требуют честной capability-карты. Недокументированные возможности не используются как гарантированный контракт.
- Сетевой результат может быть неизвестен; безопасная остановка требует ручного решения вместо обещания exactly-once.
- Локальные файлы и Google одновременно редактируются; three-way/etag/checkpoints уменьшают риск, но не создают межсистемную атомарность.
- Файлы с данными и backups доступны обладателю папки; tokens исключены. Папка в стороннем облачном синхронизаторе может получить conflict copies: они валидируются, не сливаются автоматически.
- Первый full scan и фото могут быть медленными/ограниченными квотой; прогресс, отмена и частичный безопасный результат обязательны. Quota не оправдывает skip данных.
- OAuth Testing и Workspace admin restrictions влияют на вход; это понятные состояния приложения и отдельные release dependencies.

## 18. Альтернативы и компромиссы

- vCard как основной формат: удобен для адресных книг, но не выражает People API один к одному; sidecar создаёт два источника правды. В v1 выбран JSON; vCard возможен как export позднее.
- Markdown/YAML: удобен для Obsidian, но сложнее типизация дат/массивов и обратимое представление богатых вложенных полей. Приоритет может измениться по ответу пользователя до approval.
- Electron/Tauri: подходят для UI, но добавляют другой runtime/toolchain; Avalonia/.NET выбраны для Windows desktop и изоляции sync core. Переносимость архитектуры не означает готовую macOS/Linux-сборку.
- Last-write-wins: меньше диалогов, но может терять независимые правки; выбран three-way. Мелкий merge внутри массивов отложен из-за отсутствия стабильной identity элементов.
- Incremental sync: уменьшает сеть, но token expiry/propagation усложняют первый выпуск. Full scan проще доказывать; future incremental обязан сохранять completeness и recovery контракт.
